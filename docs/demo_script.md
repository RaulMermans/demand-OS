# DemandOS — Demo Script

**Duration:** 3–5 minutes  
**Audience:** Technical reviewers, hiring managers, fellow engineers  
**Format:** Live or recorded walkthrough of the deployed app

---

## 1. Opening

> "I'm going to walk you through DemandOS — a demand forecasting and inventory risk platform
> I built as a portfolio project. This is a real ML pipeline running on Vercel with a Postgres
> database. Everything you're about to see is computed — nothing is hardcoded."

Open the browser to `https://demand-os-three.vercel.app`.

---

## 2. What DemandOS Does

> "DemandOS takes raw commerce data — orders, inventory snapshots, purchase orders — and runs
> it through a full machine learning pipeline to answer three questions:
>
> 1. What will demand look like over the next 28 days?
> 2. Which products are at risk of stocking out, and when?
> 3. Which products should we reorder, how many units, and how urgently?
>
> The answers all come from the pipeline. There are no hardcoded numbers in this dashboard."

---

## 3. Why Mock Raw Data

> "I'm using synthetic data — a realistic mock commerce dataset with 10 products,
> 2 stores, and 180 days of order history. This isn't fake data in the sense of
> fake dashboard numbers. These are raw operational records: order lines, inventory
> snapshots, and purchase orders — the same records you'd get from Shopify or an ERP.
>
> The pipeline computes everything else from scratch."

---

## 4. Pipeline Controls Walkthrough

Navigate to `/pipeline`.

> "The Pipeline Controls page is the control room. You can see the eight stages of the
> pipeline, their last run status, and run them individually or all at once.
>
> The 'Run Full Demo Pipeline' button runs all eight stages in sequence and stops on
> the first failure. This is the same button I use to reset and repopulate the demo."

Point to the durable run log (step breakdown panel).

> "Each run is recorded in the database with per-step status and error messages —
> so you can see exactly what happened and when."

---

## 5. Forecasts Page

Navigate to `/forecasts`.

> "The Forecasts page shows demand forecasts per product. I can pick any product from the
> dropdown and see the forecast line chart with p10, p50, and p90 bands.
>
> These are generated by a HistGradientBoostingRegressor trained on 30 leakage-safe features:
> lag values, rolling averages, calendar features, promotional flags, and inventory state.
> The model is trained globally across all product/store series.
>
> The p10 and p90 bands are ±1σ heuristics — I'm honest in the UI that these are
> heuristic intervals, not calibrated probabilistic ones."

---

## 6. Inventory Risk Page

Navigate to `/risks`.

> "The Inventory Risk page shows a ranked queue of product/store pairs sorted by risk tier.
> Risk tiers are deterministic — critical means the product is projected to stock out
> within the supplier lead time. High means projected inventory falls below safety stock.
>
> I compute days-until-stockout by projecting current inventory forward using
> the forward planning forecast and subtracting inbound purchase orders.
> Safety stock uses the classic formula: 1.65 σ × √lead_time."

---

## 7. Recommendations Page

Navigate to `/recommendations`.

> "The Recommendations page shows reorder suggestions ranked by urgency. Each row shows
> the product, the recommended order quantity, estimated order cost, and the reason
> the system flagged it.
>
> Operators can mark a recommendation as reviewed, approved, or ignored — but approving
> it inside DemandOS doesn't create a real purchase order. No external action is taken.
> That's an intentional safety boundary."

---

## 8. Model Performance

Navigate to `/model-performance`.

> "The Model Performance page shows the honest comparison between the ML model and
> the baseline forecasting models — seasonal naive, 7-day moving average, and 28-day
> moving average.
>
> The ML model doesn't always win on mock data with stable demand patterns —
> and I don't pretend it does. You can see the WAPE and MAE for each model type side by side."

---

## 9. Data Health

Navigate to `/data-health`.

> "The Data Health page shows the raw and canonical table counts from the database —
> products, orders, inventory snapshots, feature rows, forecast rows — all live from Postgres.
> The check list confirms referential integrity, aggregation run status, and whether
> each pipeline stage has completed.
>
> No numbers here are hardcoded. If the pipeline hasn't run yet, everything shows zero."

---

## 10. Safety Boundary

> "Before I close: let me be explicit about what DemandOS doesn't do.
>
> It doesn't create purchase orders. It doesn't email suppliers. It doesn't send
> Slack alerts. It doesn't take any external action at all.
>
> That's intentional. DemandOS is a decision support tool. The recommendations go
> to a human, who decides what to do next. This keeps the safety boundary clear."

---

## 11. Deployment Note

> "DemandOS runs in a single Vercel project: the Next.js frontend and the FastAPI backend
> are deployed from the same repository root. The database is Neon Postgres, injected
> automatically by the Vercel Marketplace integration.
>
> You can check the readiness endpoint at `/api/readiness` — it confirms the runtime mode,
> demo scale, and database connection without exposing any secrets."

Navigate to `/api/readiness` in a new tab to show the JSON.

---

## 12. Closing

> "That's DemandOS — a full raw-to-recommendation ML pipeline for retail inventory risk,
> deployed as a serverless prototype with real tests, CI, and documentation.
>
> The source code is on GitHub. Happy to walk through any specific part in more depth."

---

## Presenter Notes

- **Stay on the deployed URL** — never show localhost or `.env` files during a demo.
- **If the pipeline hasn't run**, go to `/pipeline` first and run the full pipeline.
  Small mode takes ~30–45 seconds.
- **If asked about the API key**, explain that write endpoints require a key set in
  Vercel environment variables — the key is stored in `sessionStorage` only, never
  in the database or logs.
- **If asked about real data**, explain that raw synthetic records are used — not
  fake metric outputs — and that a real Shopify connector would be the natural next step.
- **If the demo stalls**, check `/api/readiness` to confirm the backend is alive.
